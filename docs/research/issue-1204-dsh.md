## 结论摘要

源码静态证据支持两个相互串联的高可信缺陷：

1. `build_dsh_patch_yaml` 使用了多段 `\\` 续行的普通 Rust 字符串；Rust 会删除反斜杠、换行以及后续缩进空白，所以 YAML 节点层级被压平。生成文本中 `id`、`name`、`config`、`task` 不再处于预期的嵌套层级，dsh 解析 patch 后无法正常启动 headless run。
2. dsh 以失败状态退出且未产生可解析的 JSON 事件时，`summarize_stderr` 只识别小写 `error:`，也只识别行首的 `dsh:`。像 `Error: dsh: ...` 这样的首行大写前缀不会命中，函数退回 stderr 的最后一行；如果最后一行是 Node 运行时版本信息，UI 就显示 Node 版本而不是实际错误。

版本检测之所以仍可正常显示，是因为它是另一条独立路径：Core 单独执行 `dsh --version`，只依据成功退出和通用 `major.minor.patch` 解析器生成检测结果；它不生成 patch，也不经过运行失败时的 stderr 摘要逻辑。因此“检测正常”和“headless 运行失败”并不矛盾。

## 1. YAML 生成会丢失缩进

### 源码证据

[`coding_agent.rs:599-613`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/coding_agent.rs#L599-L613) 将路径和任务先用 `serde_json::to_string` 编码，然后插入普通 Rust 字符串。关键片段的每个物理源码行都用 `\` 续行：

```rust
Ok(format!(
    "# Generated by OpenLess. Applied as the last patch layer for one headless run.\n\
- insert:\n\
    - id: dsh-events\n\
      name: {path}\n\
- id: headless-runner\n\
  config:\n\
    task: {task}\n"
))
```

Rust Reference 的 [String continuation escapes](https://doc.rust-lang.org/reference/expressions/literal-expr.html#string-continuation-escapes)（证据等级 B）规定：反斜杠紧跟 LF 后，续行以及其后的空白字符都会被跳过，转义值为空序列；官方示例明确说明续行会跳过后续空格和额外换行。

因此，按源码语义而不是实机输出推导，意图中的 YAML：

```yaml
- insert:
    - id: dsh-events
      name: "..."
- id: headless-runner
  config:
    task: "..."
```

会被生成成等价于下列层级被压平的文本（路径和任务值省略）：

```yaml
- insert:
- id: dsh-events
name: "..."
- id: headless-runner
config:
task: "..."
```

这是 **A+B 静态证据，结论等级：高可信、尚未实机确认**。问题发生在 Core 的共享字符串构造层，不是 Windows `.cmd` 选择、工作目录或 dsh 版本探测层。

### 进入运行链的位置

- dsh 请求在 [`coding_agent.rs:943-979`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/coding_agent.rs#L943-L979) 组装：创建 `dsh-events.mjs` 和 `openless.patch.yml` 临时文件，设置 `DSH_PERMISSION_MODE` 与 `DSH_EVENTS_OUT=stderr`，参数为 `--profile headless --patch <patch> openless-task`。
- Tauri Host 在 [`src-tauri/src/coding_agent/mod.rs:30-51`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/src-tauri/src/coding_agent/mod.rs#L30-L51) 物化这两个文件；Windows/Unix 都写入同一份 Core 生成的 patch 内容。
- Linux egui Host 也通过相同的 `AgentMaterializationPlan` 写临时文件（[`linux-egui/src/coding_agent.rs:25-47`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/linux-egui/src/coding_agent.rs#L25-L47)）。

## 2. stderr 摘要会把真实错误替换成最后一行

### 源码证据

[`coding_agent.rs:1210-1234`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/coding_agent.rs#L1210-L1234) 只把 dsh 的 stderr 行交给 `parse_dsh_stream_line`；该解析器仅接受可解析的 JSON（[`coding_agent.rs:797-822`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/coding_agent.rs#L797-L822)）。YAML 解析失败时的普通 Node/dsh 文本不会成为流事件。

进程异常退出后，[`coding_agent.rs:1260-1271`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/coding_agent.rs#L1260-L1271) 调用 `summarize_stderr` 并发出统一 Error 事件。摘要函数在 [`coding_agent.rs:1294-1304`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/coding_agent.rs#L1294-L1304)：

- 只命中行首 `dsh:`，所以 `Error: dsh: ...` 不命中；
- 只命中小写 `error:`，所以大写 `Error:` 不命中；
- 两者都未命中时退回最后一条非空 stderr 行。

若运行时 stderr 形如 `Error: dsh: ...` 后面还有 Node 版本行，静态控制流必然选择最后一行 Node 版本。该错误消息随后由 Core Less Computer 服务作为 Error 事件发布（[`less_computer.rs:682-709`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/less_computer.rs#L682-L709)），Tauri 转发 `less-computer:event`（[`src-tauri/src/tauri_events.rs:214-228`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/src-tauri/src/tauri_events.rs#L214-L228)），面板把 `error.message` 直接显示（[`src/pages/LessComputerPanel.tsx:347-353`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/src/pages/LessComputerPanel.tsx#L347-L353)、[`src/pages/LessComputerPanel.tsx:649-653`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/src/pages/LessComputerPanel.tsx#L649-L653)）。因此 UI 显示 Node 版本是错误摘要选择的后果，而不是前端版本字段误绑定。

这是 **A 静态证据，结论等级：高可信、尚未实机确认**；“最后一行具体是 Node 版本”来自 Issue #1204 的运行报告（C），本轮没有抓取该 stderr。

## 4. 为什么版本探测仍正常

### 独立探测路径

设置页对 Codex/dsh 调用 [`coding-agent.ts:37-47`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/src/lib/ipc/coding-agent.ts#L37-L47)；Tauri 命令允许 `codex-cli`/`dsh-cli` 后调用 Core detect（[`src-tauri/src/coding_agent/commands.rs:82-102`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/src-tauri/src/coding_agent/commands.rs#L82-L102)）。Core 检测在 [`coding_agent.rs:1750-1799`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/coding_agent.rs#L1750-L1799)：

- 只执行 `dsh --version`，超时为 10 秒；
- 将 stdout/stderr 合并后调用 `parse_cli_version`；
- `installed` 只由 `exit.success` 决定；
- 不生成 patch、不加载 `headless` profile，也不运行 `openless-task`。

通用版本解析器 [`coding_agent.rs:1567-1592`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/coding_agent.rs#L1567-L1592) 会从任意 token 中提取 `major.minor.patch`，并保留 `-rc.*` 或 `+build.*` 后缀；现有单元测试覆盖 `0.1.0-rc.6`（[`coding_agent.rs:2815-2829`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/crates/openless-core/src/coding_agent.rs#L2815-L2829)）。因此 dsh `0.2.0-rc.2` 的 `--version` 成功输出可以正常显示版本，即使同一个二进制随后加载 patch 失败。

注意：该解析器不是 dsh 专用校验器，而是“第一个看起来像三段版本的 token”；若未来 `--version` 输出中把 Node 版本放在 dsh 版本之前，仍可能产生误识别。但这不是 Issue #1204 所述“探测正常、运行失败”的主要矛盾，且本轮没有实际 dsh 输出可验证。

## 5. 平台范围

- **直接受影响的共同层**：YAML 构造和 stderr 摘要在 `openless-core`，不带 `cfg(windows)`，因此任何实际启用 `DshCli` 的 Host 都共享这两个行为。
- **Windows**：Tauri Adapter 使用 `windows_executable` 处理 bare `dsh` 的 `.exe/.com/.cmd/.bat` 查找（`src-tauri/src/coding_agent/mod.rs:115-141`）；这能解释 Windows 上探测能启动 dsh，但不改变 patch YAML。Issue #1204 的 Windows Beta.4 / dsh `0.2.0-rc.2` 运行现象属于 C 级外部报告，本轮未实机复现。
- **macOS**：同一 Tauri Core/Adapter 运行链，YAML 和摘要逻辑相同；若 dsh 在该平台接受同样的 profile/patch 格式，静态缺陷同样适用。
- **Linux**：egui 有独立 Less Computer 入口（[`linux-egui/src/main.rs:879-907`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/linux-egui/src/main.rs#L879-L907)），使用 Linux Adapter（[`linux-egui/src/backend.rs:770-776`](https://github.com/Open-Less/openless/blob/1462581a0114ce43ec3822ccaaf20ad00c48c3a5/openless-all/app/linux-egui/src/backend.rs#L770-L776)）。该 Adapter 也物化 Core patch（`linux-egui/src/coding_agent.rs:25-47`），所以共同层缺陷不能仅标成 Windows 专属；但 dsh 的平台可用性及其错误文本仍需各平台运行验收。
- **Android**：本轮未找到面向 Android 的 Less Computer UI/运行验收证据；不能据源码静态材料声称 Android 受影响或已支持。
